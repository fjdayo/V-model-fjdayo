# vmodel-e2e — ユーザーストーリーから E2E を作る

V字の右端。**E2E は「利用者の導線が通しで成立するか」だけを見る。** 分岐の網羅は単体、
境界契約は結合の仕事であり、それを E2E でやると遅くて壊れやすいテストが積み上がる。

上流は `00-user-stories.md` の `US-*`。**要件から直接 E2E を起こさない。** 要件は手段を語るので、
そこから起こすと画面操作ではなく実装の写経になる。

## 1. 追加してよいかを先に決める（飛ばさない）

**UI 自動化を既定で追加しない規約のプロジェクトがある。** 勝手に足すと、誰も実行しない・
壊れても直されないテストを残すことになる。プロジェクトの規約を読み、**書き始める前に**
ユーザーへ次を提示して選ばせる。

1. 自動化を追加しない（手動QAチェック項目として書く）
2. 追加し、CI か最終ゲートで**継続実行**する
3. 追加するが継続実行しない（明示承認が要る）

3 を選ぶ場合は、**継続的な回帰防止にならないこと**・フィクスチャと保守のコスト・実行コマンドを
記録し、リリースカバレッジの owner には登録しない。

## 2. 置き場所と実行系を検出する

**決めつけない。** 次を実際に調べて、既存のやり方に合わせる。

```bash
# 既存の E2E とその設定がどこにあるか
rg --files -g '*.spec.ts' -g '*.e2e.*' -g 'playwright.config.*' -g 'cypress.config.*'
# 実行方法（package.json scripts / 専用スクリプト / CI 設定）
rg -n 'playwright|cypress' package.json */package.json .github/workflows/*.y*ml 2>/dev/null
```

- **追跡パスに置いてはいけないプロジェクトがある。** 規約が置き場所を指定していればそれに従う
- 既存の設定ファイル・ヘルパー・認証セットアップを**再利用する**。並行して2つ目の設定を作らない
- 実行成果物（スクショ・trace・レポート）の出力先も既存に合わせる

## 3. US → シナリオに展開する

**`US-*` 1つにつき、最低1本の主導線。** そのうえで、その役割に固有の失敗経路を1本足す。

| US の類型 | 起こすシナリオ |
|---|---|
| 主操作者 | 主導線1本 ＋ 主要な失敗1本 |
| 権限違いの同僚 | その役割で**できること／できないこと**を1本ずつ |
| 別テナントの他人 | 到達できないことを1本（**存在を漏らさない**ことまで見る） |
| データの消費者 | 溜まったデータを**実際に読む**1本。集計が成立することを確かめる |
| 運用者 | 運用時に必要な情報へ到達できる1本 |
| 誤操作する人 | 連打・リロード・戻る のうち、壊れると実害が出るもの |
| 使えなくなる人 | キーボードのみ・小画面 のうち、規約が要求するもの |

**「データの消費者」と「運用者」を落とさない。** ここが落ちると、書き込みだけ緑で
「後から読めない」ことに誰も気づかないまま出荷される。

## 4. シナリオ1本の構造

```
前提 → 操作 → 観測 → 後始末
```

- **前提**: どのユーザーで、どんなデータがある状態か。前提を作る手順もテスト内に置く
- **操作**: 利用者が実際にやることだけ。API 直叩きで近道しない（それは結合テストの仕事）
- **観測**: 利用者に見えること ＋ **見えないが起きているべきこと**（後述）
- **後始末**: 変えた共有状態を戻す。戻せない副作用は、テストが積み上げても壊れない設計にする

## 5. セレクタ

**利用者が見ているもので選ぶ。** 役割とアクセシブル名（`getByRole` / `getByLabel` /
`getByText`）を優先し、CSS クラスや DOM 構造に依存しない。実装の見た目を変えただけで
落ちるテストは、回帰を守らずに保守コストだけ出す。

テスト専用属性を足すのは、**役割と名前では一意に取れないときだけ**。

## 6. 独立性と後始末

- **実行順に依存しない。** 各シナリオは単独で、任意の順で、繰り返し通ること
- 共有データを変えたら戻す。戻す処理は失敗時にも走る形にする
- **繰り返し実行で行が積み上がる**種類の機能（履歴・イベント台帳など）は、
  総件数ではなく**差分**（実行前後の増分）で検証する
- 並列実行するなら、シナリオ間でデータが衝突しないことを確かめてからにする

## 7. 認証と複数ユーザー

- ログイン手順を毎回踏まない。保存済みセッション（`storageState` 等）を使い、
  ログイン自体を検証するシナリオだけフォームを通す
- **役割ごとにセッションを用意する。** 1ユーザーで権限テストを代表させない
- **認証情報を spec に書かない。** 環境変数から読み、既定値は開発用 seed に限る

## 8. UI に出ない事実を検証する

計測・監査・イベント記録のように、**成果が画面に出ない機能**がある。
このとき UI だけを見るテストは「押せた」しか確認しておらず、機能の価値を1つも検証していない。

- DB・API・ログのうち、その機能の成果が実際に残る場所を直接読む
- 読み取りは最小限にし、テストのための書き込みは避ける（やむを得ない場合は後始末する）
- **相互の突合まで見る。** 「行が増えた」ではなく「増えた行が、いま作られたものと結び付いている」

## 9. 証跡と記録

- 失敗したときに原因が分かるものを残す（スクリーンショット・trace・実行したクエリと結果）
- 機能ごとに `test-spec.md`（シナリオと US の対応）と `test-results.md`（実行日・コマンド・結果）を置く
- 実行と PASS の記録は、規約によってはコーディングエージェントの完了条件に**含めない**

## 10. 既存 E2E への影響

**変更が既存の E2E を壊すなら、黙って直さない。** 影響を開示し、
「この変更に含めて更新／別スコープで削除／そのまま残す」をユーザーに選ばせる。

```bash
# 変更する列・関数・文言を、E2E も含めて洗う。head で切らない
rg -n '<変更する識別子>' --glob '*.spec.ts' --glob '*e2e*'
```

## 完了条件

- すべての `US-*` が最低1本の `E2E-*`（または `QA-*` / `N/A: 理由`）を持つ
- 「データの消費者」「運用者」のシナリオがある、または `N/A: 理由` がある
- 各シナリオが単独・任意順・繰り返しで通る
- UI に出ない成果を持つ機能では、その成果を直接検証している
- 既存 E2E への影響を洗い、ユーザーの選択を得た
- 実行コマンドと結果を記録した

## Red Flags

- 要件から直接 E2E を起こした → US に戻る。手段ではなく利用者の目的から起こす
- 主操作者の正常系しかない → 権限違い・別テナント・消費者・運用者を1周する
- 権限テストを1ユーザーで代表させている → 役割ごとにセッションを用意する
- 画面操作を API 直叩きで飛ばしている → それは結合テスト。E2E は導線を通す
- CSS クラスや DOM 構造でセレクタを組んだ → 役割とアクセシブル名にする
- 総件数を期待値にハードコードした → 実行のたびに壊れる。差分で見る
- 計測・監査機能で「押せた」しか見ていない → 残るはずの場所を直接読む
- 既存 E2E を黙って書き換えた → 影響を開示して選ばせる
- 規約を確認せず UI 自動化を足した → 追加してよいかを先に決める
