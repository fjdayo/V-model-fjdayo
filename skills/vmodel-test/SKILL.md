# vmodel-test — テスト設計・実装・ミューテーション

V字の右側。**テストは要件の裏返しであり、要件 ID を持たないテストと、テストを持たない要件は、どちらも欠陥。**

## 1. テスト設計（`07-test-plan.md`）

各テストは `[UT-011] REQ-F-001 異常系: ...` の形で、**検証する要件 ID を必ず持つ**。

### 層の分け方

| 層 | 検証するもの | 目安 |
|----|------------|------|
| `UT-*` 単体 | 純粋なロジック、不変条件、境界値、エラー分岐 | 依存はすべて実物か、境界を1つだけ差し替える |
| `IT-*` 結合 | 実 DB・実トランザクション、認可、原子性、非機能の実測 | 隔離された依存を用意して落ちるときは落ちる |
| `E2E-*` | 利用者の導線が通しで成立するか | プロジェクト規約の置き場所に従う |

**モックで固めた単体テストは、`REQ-N-004`（原子性）や認可を検証できない。** それらは `IT-*` に置く。

### ケースの作り方（要件1つにつき最低これだけ）

`06-detailed-design.md` の「エラー」表と「境界値」から機械的に展開する。

| 種別 | 出どころ | 例 |
|------|---------|-----|
| 正常系 | 受け入れ基準の各行 | `[UT-011] REQ-F-001 正常系: 子要素ごと複製される` |
| 異常系 | `DES-*` のエラー表の各行 | `[UT-013] REQ-F-001 異常系: 他組織の ID は NotFound` |
| 境界値 | `DES-*` の境界値の各値 | `[UT-014] REQ-F-001 境界値: 子要素0件で複製できる` |
| 不変条件 | `ENT-*` の INV 表の各行 | `[UT-015] INV-002 子項目の orgId が親と異なる場合は保存されない` |

**境界値は「両側」を書く。** 上限 120 字が通ることだけ書いて 121 字を書かないと、`<=` を `<` に変えても、`<` を `<=` に変えても検出できない。

### 回帰テスト範囲（必須章）

`03-architecture.md` の「影響範囲と従属関係」表の**既存テスト列をそのまま持ってくる**。

```markdown
## 回帰テスト範囲

| 変更対象 | 影響を受ける既存テスト | 実行コマンド | 結果 |
|---------|--------------------|------------|------|
| `sampleRepo.findById` | `detail.test.ts`, `export.test.ts` | `pnpm test src/lib/sample` | — |
| `sample_item.org_id` | `IT-004` | `pnpm test:integration -t IT-004` | — |
```

新規テストが緑でも、**この表の既存テストを実行するまでフェーズを完了にしない。** 新規テストは自分が壊したものを見つけない。

### E2E の網羅性

**シナリオの起こし方・置き場所・追加してよいかの判断は `vmodel-e2e` が持つ。** ここでは網羅性だけ見る。

網羅の基準は**要件ではなくユーザーストーリー**（`00-user-stories.md` の `US-*`）。
要件から E2E を起こすと、手段の写経になって利用者の導線を通さない。

すべての `US-*` と、すべての `REQ-F-*` が次のどちらかを持つ:

- `E2E-*`（最低ライン: 主要導線1本 ＋ 異常系1本）
- `N/A: <理由>`（例: `N/A: UI を持たない内部処理。IT-003 で担保`）

UI 自動化を既定で追加しない規約のプロジェクトでは、`E2E-*` の代わりに**採番した手動QAチェック項目 `QA-nnn`** を書く。
「手動QAで確認する」という散文で済ませない。ID が無いと台帳の `E2E` 列に書けず、grep 検証からも外れる。

- 項目には**対象画面・操作・ビューポートまたは状態・期待結果**を必ず含める
- 台帳の `E2E` 列に `QA-*` を書く（列名は変えない）
- 実行や PASS の記録はこのスキルの完了条件に**含めない**（実施はユーザー側の作業）

```markdown
### [QA-003] REQ-F-001 正常系: 複製ボタンから一覧先頭に複製が現れる
- 画面: SCR-002 サンプル一覧 / ビューポート: 1280x800 と 375x812
- 操作: 任意のサンプル行の複製ボタン → 確認ダイアログで実行
- 期待結果: 一覧先頭に `<元の名前>のコピー` が1件増える。元の行の更新日時は変わらない
```

## 2. テスト実装

- 名前は `[UT-011] REQ-F-001 <種別>: <期待する挙動>`。ID を素の文字列で書く（grep 検証が効く）。
- **期待値をハードコードする。** 実装と同じ計算式で期待値を作ると、実装が間違ったまま緑になる。
- 異常系は「例外が出た」ではなく**エラーの種類と、そのときデータがどうなったか**まで検証する。ロールバックの検証を省くと `REQ-N-004` は未検証のまま。
- テストを追加したら、その場で台帳の `UT` / `IT` / `E2E` 列に追記する。

## 3. ミューテーションテスト（変更ファイルのみ）

**目的はスコアを上げることではなく、生存 mutant を「書き忘れた異常系テスト」として拾うこと。**

```bash
# 対象は今回の変更分だけ。全体に広げると時間もトークンも一気に溶ける
# ベースブランチは PR のマージ先。Phase 0 で確認した値を使い、origin/main と決めつけない
BASE_BRANCH=<Phase 0 で確認したマージ先>          # 例: origin/staging
BASE=$(git merge-base HEAD "$BASE_BRANCH")
git diff --name-only "$BASE"...HEAD -- '*.ts' '*.js' | grep -vE '\.(test|spec)\.'
```

**ファイル数が「自分で変更した覚え」と合わなければ基点が違う。** そのまま進めない。
既定ブランチが実際のマージ先から大きく遅れているリポジトリでは、`origin/main` を基点にすると
無関係な数十ファイルが対象に入り、mutation が終わらない。基点を直してから実行する。

**まずツールが導入済みかを確認する。** 未導入のリポジトリで `npx stryker` を叩くと、
ツールチェーン一式のダウンロードが走る。**勝手に入れない。** 手動フォールバックへ回す。

```bash
# 導入済みか（package.json / 設定ファイルのどちらかに実体があるか）
grep -rl stryker package.json */package.json */*/package.json 2>/dev/null; ls stryker.conf.* 2>/dev/null

# 導入済みのときだけ実行する
npx stryker run --mutate "src/lib/sample/copy.ts,src/lib/sample/repo.ts"
```

他言語では同等のツールを使う（Python: `mutmut` / `cosmic-ray`、Java: `PIT`、Go: `go-mutesting`、Rust: `cargo-mutants`）。
**ツールが無い／未導入でも工程を飛ばさない。** その場合は `06-detailed-design.md` の境界値・エラー表を1行ずつ手で反転させ（`>` ↔ `>=`、`&&` ↔ `||`、`throw` を削除、早期 return を削除、条件を `true` 固定）、落ちるテストがあるかを確認する。

### 生存 mutant の処理

生存 mutant 1件ごとに、次のどれかに分類して `08-review.md` に記録する。**「スコアが十分だから無視」は使わない。**

| 分類 | 対処 |
|------|------|
| テスト不足 | 異常系／境界値テストを追加する → 台帳の `UT` 列に追記 |
| 到達不能コード | そのコードを削除する（テストを足すのではない） |
| 等価変異（挙動が変わらない） | 理由を1行書いて除外する。**「たぶん等価」は不可。** 挙動が同じであることを説明できるときだけ |

```markdown
### mutation 結果（変更ファイル 2件）

| # | 場所 | 変異 | 判定 | 対処 |
|---|------|------|------|------|
| 7 | `copy.ts:42` | `n > 0` → `n >= 0` | 生存 → テスト不足 | UT-014（子要素0件）を追加 |
| 12 | `copy.ts:58` | `throw NotFound` 削除 | 生存 → テスト不足 | UT-013 が例外種別を見ていなかった。修正 |
| 19 | `repo.ts:31` | ログ文言の変更 | 生存 → 等価変異 | 文言は仕様外。除外 |
```

テストを追加したら mutation を再実行し、対処した mutant が殺せていることを確認する。

## 完了条件

- すべてのテストが `REQ-*` または `INV-*` の ID を名前に含む
- すべての `REQ-F-*` に正常系・異常系の両方がある
- `DES-*` のエラー表・境界値の各行に対応するテストがある
- 回帰テスト範囲の既存テストを実行し、結果を表に記入した
- 生存 mutant がすべて「対処済」または「除外理由あり」に分類されている
- 台帳の `UT` / `IT` / `E2E` 列に空欄が無い

## Red Flags

- E2E を要件から起こした → `US-*` から起こす。`vmodel-e2e` を読む
- 主操作者の正常系しか E2E が無い → 権限違い・別テナント・データの消費者・運用者を1周する
- テスト名に要件 ID が無い → 台帳と繋がらない。付ける
- 異常系が `expect(() => f()).toThrow()` だけ → エラー種別とデータの状態まで検証する
- 境界値が片側だけ → 反対側を足す
- 期待値を実装と同じ式で計算している → ハードコードに直す
- 生存 mutant を「スコアは十分」で流した → 1件ずつ分類する
- mutation を全ファイルに掛けようとしている → 変更差分だけに絞る
- 新規テストだけ緑にして完了とした → 回帰テスト範囲の既存テストを実行する
- `REQ-N-*` の検証手段が空 → 測れないなら要件を書き直す
