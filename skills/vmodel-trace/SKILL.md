# vmodel-trace — 採番とトレーサビリティ台帳

V字モデルの背骨。**すべての成果物に同じ ID トークンをリテラルで埋め込み、`grep` を検証器にする。**
台帳と実体は別々に嘘をつけるので、常に grep の結果を正とする。

## ID 体系

| 接頭辞 | 対象 | 例 |
|---|---|---|
| `US-nnn` | ユーザーストーリー（すべての上流） | `US-001` |
| `SCR-nnn` | 画面・領域・状態 | `SCR-002` |
| `SCR-nnn-Fnn` | 画面項目（入力欄・表示項目・アクション） | `SCR-002-F03` |
| `REQ-F-nnn` | **機能**要件 | `REQ-F-001` |
| `REQ-N-nnn` | **非機能**要件 | `REQ-N-003` |
| `ARC-nnn` | アーキテクチャ判断 | `ARC-001` |
| `DFD-nnn` | データフロー・シーケンス | `DFD-004` |
| `ENT-nnn` | エンティティ・集約 | `ENT-002` |
| `INV-nnn` | 不変条件（`ENT-*` に属する） | `INV-002` |
| `DES-nnn` | 詳細設計（モジュール／関数単位） | `DES-011` |
| `UT-nnn` | 単体テスト | `UT-011` |
| `IT-nnn` | 結合テスト | `IT-003` |
| `E2E-nnn` | E2Eテスト | `E2E-002` |
| `QA-nnn` | 手動QAチェック項目（UI 自動化を追加しない規約のとき `E2E-*` の代わり） | `QA-003` |

**採番規則**

- 3桁ゼロ埋め。機能（`docs/vmodel/<slug>/`）ごとに 001 から独立採番する。
- **欠番を詰めない。** 削除した項目の番号は再利用せず、台帳に `状態: 廃止` で残す。番号を再利用すると過去のレビュー記録や Git 履歴の参照先が静かにずれる。
- 実装コードには ID を振らない。コード側は `@impl` コメントで既存 ID を指す。

## ID の埋め込み方（これをやらないと grep が効かない）

| 成果物 | 書き方 |
|---|---|
| ドキュメント | 見出しに `### [REQ-F-001] サンプルを複製できる` |
| 実装コード | 関数直上に `// @impl REQ-F-001, REQ-N-003` |
| テスト | テスト名に `it('[UT-011] REQ-F-001 異常系: 権限のない組織のサンプルは複製できない')` |

**追跡ファイルに ID を書けない場合がある。** 次のどちらかに当たったら、コードとテストには ID を
埋め込まず、**台帳の `実装` / `UT` / `IT` 列にパスとテスト名を書いて対応づける**。

- プロジェクトの既存規約が ID 入りのテスト名・コメントを持たない（先例0件なら規約を優先する）
- 台帳がリポジトリ外・追跡外にある（この場合、追跡コード中の ID は**定義が存在しない参照**になり、
  PR のレビュアーから辿れない）

このとき grep 検証は成果物ディレクトリの中だけで閉じる。コード側の対応づけは台帳のパス列が担い、
`陳腐化`（パスが実在するか）のチェックで代替する。
| 台帳 | 表のセルにそのまま `REQ-F-001` |

ID は**必ず素の文字列**で書く。`REQ-F-{n}` のような変数展開や、`REQ‑F‑001`（U+2011 の非破壊ハイフン）を使わない。grep が拾えなくなる。

## 台帳フォーマット

`docs/vmodel/<slug>/00-traceability.md`

```markdown
# トレーサビリティ台帳: <機能名>

最終更新: YYYY-MM-DD / 対象ブランチ: <branch>

## 要件トレーサビリティ

| ID | 種別 | 内容 | 上流 | 設計 | 実装 | UT | IT | E2E | 状態 |
|----|------|------|------|------|------|----|----|-----|------|
| REQ-F-001 | 機能 | サンプルを複製できる | SCR-002 | DFD-004, DES-011 | `src/lib/sample/copy.ts` | UT-011, UT-012 | IT-003 | E2E-002 | 実装済 |
| REQ-N-003 | 非機能 | 複製 p95 < 300ms | SCR-002 | ARC-002 | `src/lib/sample/copy.ts` | N/A: 性能は単体で測れない | IT-009 | N/A: 計測は IT-009 で担保 | 実装済 |

## 廃止・保留

| ID | 内容 | 理由 | 日付 |
|----|------|------|------|

## 最終検証結果

実行日 / コマンド / 結果（後述の検証手順の出力をそのまま貼る）
```

**空欄を作らない。** セルに書けるのは次の3種だけ。空セルは「まだ考えていない」と「考えた上で不要」を区別できず、台帳が信用を失う。

| 書式 | 意味 |
|---|---|
| ID またはパス | 下流が存在する |
| `未` | まだ着手していない（下流列の初期値。Phase 1 で要件行を作った直後はここ） |
| `N/A: <理由>` | 考えた上で不要。理由を省略しない |

`状態` は `要件確定` → `設計済` → `実装済` → `検証済` → `廃止` のいずれか。**これは要件1件のライフサイクルであって、フェーズの進捗ではない。** 進捗の判定には使わない。

UI 自動化を追加しない規約のプロジェクトでは、`E2E` 列に `QA-*` を書く（列名は変えない）。

## 検証手順（スクリプト不要）

**フェーズによって対象 ID を変える。** `UT-*` / `IT-*` / `E2E-*` / `QA-*` はテスト設計フェーズで
採番されるため、要件・設計フェーズの時点では台帳に存在しない。上流成果物がそれらを
「検証先」として先に参照するのは正しい書き方なので、**要件・設計フェーズの検証では
下流テスト ID を PAT から外す**。外さないと必ず偽の孤立が出て、検証そのものが信用されなくなる。

| 実行時点 | PAT に含める接頭辞 |
|---|---|
| 要件・設計フェーズ | `US｜SCR｜REQ-F｜REQ-N｜ARC｜DFD｜ENT｜INV｜DES` |
| テスト設計フェーズ以降 | 上記 ＋ `UT｜IT｜E2E｜QA` |

```bash
SLUG=docs/vmodel/<slug>
# 実装・テストの実パス。Phase 0 で確認した値を入れる。src tests のまま実行しない
CODE="<実装ディレクトリ> <テストディレクトリ>"   # 例: apps/web/src packages windows-local/local-test
PAT='\b(US|SCR|REQ-F|REQ-N|ARC|DFD|ENT|INV|DES|UT|IT|E2E|QA)-[0-9]{3}(-F[0-9]{2})?\b'

# 1. 台帳漏れ（孤立）: 実体にあるが台帳に無い ID
comm -23 \
  <(grep -rhoE "$PAT" "$SLUG" $CODE --exclude=00-traceability.md 2>/dev/null | sort -u) \
  <(grep -ohE "$PAT" "$SLUG/00-traceability.md" | sort -u)

# 2. リンク切れ: 台帳にあるが実体がどこにも無い ID
comm -13 \
  <(grep -rhoE "$PAT" "$SLUG" $CODE --exclude=00-traceability.md 2>/dev/null | sort -u) \
  <(grep -ohE "$PAT" "$SLUG/00-traceability.md" | sort -u)

# 3. 未消化: 特定 ID の出現箇所を全部見る（テストが無い要件を目視で確定）
grep -rn 'REQ-F-001' "$SLUG" $CODE
```

`$CODE` は**必ず実パスに置き換える。** モノレポでは `src` `tests` は存在しないことが多く、
`2>/dev/null` でエラーが消えるため、**間違ったまま実行しても正常終了する。**
E2E や手動QA項目がリポジトリ外（例: `windows-local/local-test/`）にある場合は、その実パスも足す。

**検出される異常と対処**

| 異常 | 意味 | 対処 |
|---|---|---|
| 孤立 | 根拠となる上流を持たない項目 | 上流要件を書くか、その項目を削除する |
| 未消化 | 下流（実装・テスト）が空の要件 | テストを足すか、`N/A: 理由` を書く |
| リンク切れ | 存在しない ID を参照 | 参照先を直す。ID を作り直さない |
| 陳腐化 | 台帳の `実装` 列のパスが存在しない | パスを追う。移動なら更新、削除なら `廃止` へ |

## 更新タイミング

台帳は**成果物を書いた直後に同じ変更で更新する。** 後でまとめて直すと、必ず実体と乖離する。
特に mutation テストで異常系テストを追加したときは、その場で `UT` 列に追記する。

## Red Flags

- 台帳のセルが空 → `N/A: 理由` を書くまで先に進まない
- 「あとで台帳を直す」 → その場で直す
- ID を振り直して欠番を詰めた → 過去の参照が壊れる。戻す
- grep で 0 件なのに台帳に載っている → 実体が無い。台帳が嘘をついている
- 実装・テストの ID がまとめて「リンク切れ」に出た → 台帳ではなく `$CODE` のパスを疑う。読み替え漏れ
- 進捗を `状態` 列から読もうとしている → `状態` は要件のライフサイクル。進捗は成果物と下流列で見る
