# /vmodel — V字モデル・トレーサビリティ駆動開発

対象: `$ARGUMENTS`

左側（要件・設計）で3回だけ止まり、右側（実装・テスト・レビュー）は走り切る。
すべての成果物は `vmodel-trace` の ID で相互に引ける状態を保つ。

## Phase 0: 前提確認（必ず最初）

1. `git status` と現在ブランチを確認する。
2. **プロジェクト規約を検出し、これを `/vmodel` より優先する。**
   `CLAUDE.md` / `AGENTS.md` / `CLAUDE.local.md` / `docs/` の規約文書を読む。特に次を確認:
   - 計画ファイルの要否と置き場所（例 `docs/plans/`）
   - テストの所有権・カバレッジ規約（例 coverage manifest、unit-required の判定）
   - E2E / UI自動化の可否と置き場所（**追跡パスに置いてはいけないプロジェクトがある**）
   - レビュー履歴の記録先（例 `docs/code-review-histories/YYYY-MM-DD.md`）
   - コミット・プッシュの承認ゲート
   規約と `/vmodel` の既定がぶつかったら**規約を採用し、その旨をユーザーに1行で伝える**。
3. 検証コマンドを検出する（`package.json` scripts / Makefile / CI 設定）。テスト・lint・型チェック・ビルド・mutation の各コマンドを控える。
   あわせて次の3つを控える。**いずれも既定値を決めつけない。**
   - **ベースブランチ（PR のマージ先）**。`origin/main` とは限らない。Phase 5 の mutation 対象の基点になる
   - **mutation ツールが導入済みか**（Stryker 等）。未導入なら勝手に入れず、手動反転にフォールバックする
   - **実装とテストの実パス**（例 `apps/web/src`、追跡外の E2E 置き場）。`vmodel-trace` の grep 検証の対象になる。
     `src` `tests` のまま実行すると、モノレポでは全 ID が偽の「リンク切れ」になる
4. `<slug>` と**成果物の出力先**を決める。
   - `<slug>` は `--slug` 指定があればそれ、無ければ機能名の kebab-case
   - 出力先の既定は `docs/vmodel/<slug>/`。ただし**プロジェクトの docs 構成に無いディレクトリを黙って新設しない。**
     規約が別の置き場所を持つ（機能ドキュメントの所定位置、追跡外に置く決まり等）ならそちらに合わせる。
     9ファイルがどこに増えるかを**ゲート1で場所ごと提示して承認を得る。**
   - 出力先が既にあれば `--resume` 扱い。再開フェーズは**成果物の有無と台帳の下流列**で判定する。
     `状態` 列は要件1件のライフサイクルであって進捗ではないので、判定に使わない。

   | 再開先 | 判定 |
   |---|---|
   | Phase 1 | `00-user-stories`/`01`/`02` か台帳が無い |
   | Phase 2 | `00-user-stories`/`01`/`02` はあるが `03`〜`06` のどれかが無い |
   | Phase 3 | `03`〜`06` はあるが `07` が無い |
   | Phase 4 | `07` はあるが台帳の `実装` 列に `未` がある |
   | Phase 5 | `実装` 列は埋まったが `UT`/`IT`/`E2E` 列に `未` がある |
   | Phase 6 | 下流列は埋まったが `08` が無い |
   | Phase 7 | `08` はあるが台帳の「最終検証結果」が空 |

   **迷ったら手前のフェーズから再開する。** 進みすぎると、空の下流列を残したまま実装に入る。
5. TodoWrite で Phase 1〜8 の骨組みを作る。

`--phase N` が指定された場合は Phase 0 のあと該当フェーズだけ実行する。

## Phase 1: 要件（ゲート1）

`vmodel-requirements` スキルを使い、**この順で**作る。

- `00-user-stories.md` — `US-*`。**誰のために作るのかを先に決める。**
  利用者の7類型（主操作者／権限違いの同僚／別テナントの他人／**データの消費者**／**運用者**／
  誤操作する人／使えなくなる人）を1周し、該当なしは `N/A: 理由` を書く
- `01-screen-spec.md` — `SCR-*`。**画面項目 ↔ データ項目の対応表を必須**
- `02-requirements.md` — `REQ-F-*` / `REQ-N-*`。機能要件と非機能要件を**別の章に物理的に分離**。
  すべての `REQ-F-*` が上流に最低1つの `US-*` を持つ
- `00-traceability.md` — 台帳を新規作成し、US 行と要件行を埋める（下流列は `未` のまま）

**⏸ ゲート1**: **ユーザーストーリー一覧**と要件一覧（ID・内容・上流）を提示してユーザーの承認を待つ。
特に「この利用者を忘れていないか」を見てもらう。承認なしに Phase 2 へ進まない。

## Phase 2: 設計（ゲート2）

`vmodel-design` スキルを使い、次を作る。

- `03-architecture.md` — `ARC-*`、**影響範囲と従属関係の表**（触る関数の呼び出し元を grep で全部洗う）、**結合度の評価**
- `04-dataflow.md` — `DFD-*`（mermaid sequenceDiagram / flowchart）
- `05-domain-model.md` — `ENT-*`（mermaid erDiagram + 集約・境界づけられたコンテキスト・ユビキタス言語・不変条件）
- `06-detailed-design.md` — `DES-*`
- 台帳の `設計` 列を埋める

**⏸ ゲート2**: 設計の要点と、要件→設計の対応（台帳の該当列）を提示して承認を待つ。

## Phase 3: テスト設計（ゲート3）

`vmodel-test` スキルの「テスト設計」節と、E2E は `vmodel-e2e` スキルを使って `07-test-plan.md` を作る。

- `UT-*` / `IT-*` を採番し、**正常系・異常系・境界値をケース単位で分ける**
- **`E2E-*` は `US-*` から起こす。要件から起こさない**（手段の写経になり導線を通さない）。
  役割ごとに主導線1本＋その役割固有の失敗1本。**データの消費者と運用者を落とさない**
- **回帰テスト範囲**を `03-architecture.md` の影響範囲表から引き写す（影響を受ける既存テストと実行コマンド）。
  **既存 E2E も grep 対象に入れる**（`head` で切らない）
- すべての `US-*` と `REQ-F-*` が E2E 列を持つか、`N/A: 理由` を持つ
- UI 自動化の追加可否は `vmodel-e2e` の3択をユーザーに選ばせてから決める。
  追加しない規約なら手動QAチェック項目 `QA-*`（画面・操作・状態・期待結果）として書く
- 既存 E2E を壊す変更なら、**黙って直さず**影響を開示して扱いを選ばせる
- 台帳の `UT` / `IT` / `E2E` 列を埋める

**⏸ ゲート3**: テストケース一覧を提示して承認を待つ。特に異常系の拾い方に抜けが無いか見てもらう。

**このゲートを越える前に、Phase 0 で検出した規約のうち「実装前」を要求するものを済ませる。**
Phase 8 の最終報告に回さない。実装が始まってからでは規約違反が確定する。典型的には:

- 計画ファイル（例 `docs/plans/`）— 「コーディング作業の前に」と書かれていれば Phase 4 より前
- テスト所有権・カバレッジ規約（例 coverage manifest の owner 決定）— 「承認を求める前に計画へ含める」ならここ
- UI 自動化の可否の確認 — 自動化を足すかどうかをユーザーに選ばせる規約なら、この承認と同時に聞く

## Phase 4〜8: ここから止まらない

### Phase 4: 実装

- `superpowers:test-driven-development` に従う。プロジェクトに `ddd-workflow` 等の実装規約スキルがあればそれを優先する。
- 実装した関数の直上に `// @impl REQ-F-001` を付ける。
- 台帳の `実装` 列を埋める。

### Phase 5: テスト実装と mutation

`vmodel-test` スキルの「テスト実装」「ミューテーション」節に従う。

1. `UT-*` を実装 → 実行して緑にする
2. **変更したファイルだけ**を対象に mutation を実行する。基点は Phase 0 で控えたベースブランチ。
   対象ファイル数が「自分で変更した覚え」と合わなければ基点が違う。直してから実行する。
   ツールが未導入なら**入れずに**手動反転にフォールバックする（`vmodel-test` の該当節）
3. 生存 mutant を「足りない異常系テスト」として扱い、テストを追加 → 台帳の `UT` 列に追記
4. `IT-*` → `E2E-*`（`vmodel-e2e` に従う。置き場所・実行系・証跡は既存の仕組みを再利用する）

### Phase 6: 6観点レビュー

次の6エージェントを **1回の応答でまとめて並列起動**する。各エージェントには「変更範囲（diff のファイル一覧）」「`docs/vmodel/<slug>/` のパス」「対象の ID 一覧」を渡す。

| エージェント | 観点 |
|---|---|
| `review-naming-structure` | 命名・構造 |
| `review-local-quality` | 局所品質 |
| `review-dataflow` | データフロー |
| `review-security` | セキュリティ・機密 |
| `review-compliance` | 法令規制 |
| `review-dependency` | 依存関係互換性 |

結果を `08-review.md` に、観点別・重大度別（P0〜P3）に整理して記録する。

**記録の前に必ず名寄せする。** 6観点は範囲が重なるので、同じ欠陥が別々の観点から別の重大度で上がる。

- 同一箇所・同一原因の指摘は1件に統合し、上がった観点をすべて併記する
- 重大度が割れたら**高いほうを採る**。低いほうを採るなら理由を書く
- 観点をまたいで対処案が矛盾したら、両案を残して Phase 8 の「確認事項」へ上げる。片方を黙って捨てない

**P0 と P1 はこのフェーズ内で直す。** P2 は直すか、直さない理由を書く。P3 は記録のみ。
修正したら Phase 5 の検証コマンドを再実行する。

### Phase 7: 収束

`vmodel-trace` の検証手順を実行して孤立・未消化・リンク切れをゼロにする。
そのうえで `/audit` を `docs/vmodel/<slug>` を対象に実行し、新規指摘がゼロになるまで回す。

### Phase 8: 最終報告

- 成果物一覧と、台帳のカバレッジ（要件数 / 実装済 / テスト済 / E2E済 / N/A 内訳）
- mutation の結果（生存 mutant と、それに対して追加したテスト）
- 6観点レビューの P0〜P3 件数と、未対応の残件
- **確認事項**: 判断が要るもの（仕様解釈・スコープ・承認欄）は自動で埋めず、論点＋推奨案＋代替案で列挙する
- Phase 0 で検出した規約のうち、**ゲート3で済ませたもの以外**の残作業を明示する（レビュー履歴の記録など、実装後にしか書けないもの）
- **コミット・プッシュ・PR作成はしない。** ユーザーが差分を確認して明示的に指示するまで待つ

## 全フェーズ共通

- 承認欄・ゲート判定など人間の意思決定を代行して埋めない。
- スコープを広げない。監査のついでの無関係なリファクタを混ぜない。
- 成果物とやり取りはユーザーの会話言語で書く。
