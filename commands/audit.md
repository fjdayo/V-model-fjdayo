# /audit — トレーサビリティ・レビューループ

このコマンドはアカウント単位のコマンド(`~/.claude/commands/audit.md`)であり、どのプロジェクトでも使える。**プロジェクトごとに規約が違う前提で、まず規約を検出してから動く。**

対象: `$ARGUMENTS`
- 空欄 → プロジェクト全体を対象にする
- パスまたはID(例 `docs/specs/06-basic-design.md`, `US-010`, `src/services/foo.ts`) → その要素と、トレースチェーン上の上流・下流一式を対象にする
- `--quick` → `git diff` / 直近コミットに関係する範囲だけに絞る

## Phase 0: 前提確認

1. `git status` で作業ツリーの状態を確認する。他セッションが並行編集している可能性があるため、判断の根拠にするファイルは都度読み直し、鮮度を確認してから使う(git履歴・コミットは正、記憶や以前読んだ内容を過信しない)。
2. プロジェクトの規約を検出する:
   - 開発プロセス文書(例 `docs/process/*.md`)、トレーサビリティマトリクス(例 `docs/trace/*traceability*.md` や類似)、テンプレート集、ID命名規則(`XX-000` 形式の接頭辞とその定義元)、フェーズゲート記録があれば、**それをそのまま正とする**。命名・カバレッジ基準・承認フローを独自に作り替えない。
   - そうした規約が存在しないプロジェクトでは、README/要求仕様/設計ドキュメント群を上流、`src`等の実装を中流、テストを下流とみなし、ファイル名・関数名・コメント中の参照・importグラフから対応関係を推定する(汎用モード)。
3. 検証コマンドと変更管理台帳の有無を調べる:
   - `package.json`のscripts、Makefile、CI設定等から、テスト・lint・型チェック・ビルドに相当するコマンドを検出しておく(例 `npm test`, `npm run lint`, `tsc --noEmit`)。Phase 2〜4で自動修正のたびに実行する。
   - 変更管理台帳(例 `docs/trace/change-requests.md` のようなCR台帳、issueテンプレート等)がプロジェクトにあれば所在と採番規則を把握しておく。Phase 5で「要確認」項目の起票案作成に使う。
4. TodoWriteで「Phase1: マップ構築」「Phase2〜4: レビューループ(ラウンドNごとに追加)」「Phase5: 最終報告」の骨組みを作る。

## Phase 1: トレーサビリティマップの構築・更新

対象範囲について、上流→下流の連鎖(要求/要件 → 設計 → 実装ファイル → テスト、該当すればさらに評価指標まで)を洗い出す。

- 各要素(ID、または要件・仕様の単位)ごとに「上流あり/なし」「下流(設計/実装/テスト)あり/なし」を突き合わせる。
- 検出すべき異常:
  - **孤立**: 根拠となる上流を持たない要件・設計・コード
  - **未消化**: 下流(実装・テスト)を一切持たない要求・要件
  - **リンク切れ**: 存在しないIDやファイルへの参照
  - **陳腐化**: ドキュメントの記述と実装の実際の挙動が食い違っている
  - **マトリクス未更新**: 実体(コード・テスト)は変わっているのにトレーサビリティ表が追随していない
- 正式なマトリクスファイルが存在する場合は、そこに書かれているリンクと実コードを突き合わせて答え合わせする。存在しない/対象範囲に無い場合は、作業用のマップをその場で組み立てて使う(ファイルへの永続化は求められない限り不要)。

## Phase 2〜4: 多観点レビュー → 修正 → 収束判定(ラウンドを繰り返す)

1ラウンド = 以下の観点をひと通りチェックし、指摘を洗い出し、修正できるものは修正する。

**観点**
1. 文書間整合性 — ドキュメント同士の矛盾、用語・定義のブレ、バージョン/更新日の不整合
2. 文書⇔コード整合性 — 仕様書に書かれた内容と実装が一致しているか、ドキュメント化されていない実装挙動がないか
3. トレーサビリティの網羅性 — Phase 1で洗い出した孤立・未消化・リンク切れ・陳腐化・マトリクス未更新
4. コードの正しさ・品質 — バグ、エッジケース漏れ、プロジェクト自身の既存規約からの逸脱(新しい流儀を持ち込まない)
5. テストの妥当性 — 仕様/設計に対応するテストがあるか、そのテストが実際に仕様を検証できているか(表面的に緑なだけでないか)
6. プロセス・ゲート適合性(該当プロジェクトのみ) — ゲート記録・承認欄・テンプレート準拠、チェックリストとの整合

各指摘は次のどちらかに分類する:

- **自動修正**: 誤字、リンク切れ、ドキュメント間の単純な不整合、トレーサビリティ表の記入漏れ、明らかな記述ミスなど、判断の余地がないもの → その場で修正する
- **要確認**: 仕様解釈、スコープ変更、破壊的変更、承認・ゲート判定(PO承認欄など)に関わるもの、複数の直し方があり得るもの → **自動修正しない**。「確認事項」として蓄積する(具体的な論点+推奨案+代替案の形で)

承認欄・PO承認・ゲート判定などの人間の意思決定を代行して埋めない。AIとして根拠は示すが、判定行為そのものは行わない。修正は指摘された不整合の解消に留め、監査のついでに無関係なリファクタや改善を混ぜない(スコープを広げない)。

自動修正を適用したら、Phase 0で検出した検証コマンド(テスト・lint・型チェック・ビルド等)を**毎ラウンド**実行する。失敗は直ちに新規指摘として扱い、原因が明確なら自動修正、判断が要るなら要確認に回す。検証コマンドが存在しないプロジェクトではこの手順を省略する。

修正を適用したら、影響範囲を再度Phase 1〜2にかけ、次のラウンドを回す。TodoWriteに各ラウンドの結果(指摘数・修正数・残件数)を積み上げる。

**収束条件**: 1ラウンドを通して**新規の**指摘(自動修正・要確認とも)がゼロになったら終了する。既に「要確認」として記録済みで未解消なだけの項目は、内容が変わらない限り毎ラウンド「新規」とは数えない(=要確認が残っていること自体はループを止めない。それらは最終報告に持ち越す)。目安5ラウンドを超えても新規の自動修正が出続ける場合はループを止め、「単純な指摘の反復では解決しない構造的な問題」として報告する(無限に回さない)。

ultracodeが有効なセッションでは、観点ごとに独立したレビューエージェント+指摘ごとの敵対的検証(Workflowのpipeline/parallelパターン)を使ってよい。無効な場合はこのセッション内で素朴に反復する。

## Phase 5: 最終報告

- 実施ラウンド数、観点別の指摘数・修正数
- トレーサビリティのカバレッジ変化(マトリクスがあれば before/after)
- **確認事項**: 要確認に分類した項目を、論点・推奨案・代替案付きで列挙する。数が絞れる場合はAskUserQuestionで優先度の高いものから確認する。多い場合はリストで提示し、まとめて回答してもらう
- プロジェクトに変更管理台帳(Phase 0で検出したCR台帳等)がある場合、確認事項をその台帳の書式・採番規則に沿った**起票案**として下書きする(タイトル・概要・影響範囲まで)。実際に台帳へ書き込むのはユーザーが承認してから行い、勝手に確定登録しない。台帳が無いプロジェクトではこの手順を省略し、確認事項はチャット上のリストのみで提示する。
- 未コミットの変更が残っている場合、コミットはユーザーの明示的な依頼があるまで行わない
